대상: $ARGUMENTS (비어 있으면 docs/specs/에서 최근 수정된 spec)

목표: spec의 "무엇"을 "어떻게"로 바꾼다. 설계는 이 단계에서만 수정한다.

## 1. 읽기
- spec 파일, docs/principles.md, 관련 기존 코드 패턴을 읽는다.
- 범위 밖 항목은 설계에 넣지 않는다.

## 2. 같은 spec 파일에 작성
### 4. 설계
- 구조: 흐름/컴포넌트를 짧게 (화살표 한 줄이면 충분).
- 주요 결정: 결정과 이유를 한 줄씩. 기존 코드 재사용을 우선한다.
- 고려했지만 안 한 것: 대안과 안 한 이유.
### 5. 작업
- `- [ ] Tn 작업명 (검증: 실행 가능한 확인 방법)` 형식.
- task 하나는 한 번에 구현·검증 가능한 크기로 나눈다.
- 모든 task에 "검증:"을 넣는다. 명령, 요청, 화면 확인 등 구체적으로.

## 3. 셀프체크 출력
- AC→task 커버리지: AC1→T1, AC2→T2… 빠진 AC가 있으면 표시.
- 원칙 위반: 새 추상화, 외부 의존성, principles.md 위반 여부.
- 미해결: 구현 전에 확인할 항목과 언제까지(Tn 전).

## 4. 멈춤
- 사람 검토를 기다린다. "검토 후 /build를 실행하세요"라고 안내한다.
